# القسمان الجديدان: الذكاء الاصطناعي + واتساب

توثيق التصميم والتنفيذ للقسمين الرئيسيين المضافين للبوت (محدَّث مع الكود):

1. **🤖 الذكاء الاصطناعي** — أقسام ديناميكية (برمجة بدون قيود / دردشة بدون
   قيود / أي قسم مستقبلي) مبنية على مزود **NanoGPT**، بتكلفة رسالة لكل
   قسم وربح مضاعف، وجلسات محفوظة.
2. **📱 واتساب** — قسم مربوط بـ **بوت ثاني** يدير جلسات واتساب لكل مستخدم،
   بنظام باقات (يوم/3/7/30) وتجديد تلقائي، وتظهر كل أزرار وأوامر البوت الثاني
   داخل البوت الحالي عبر جسر `wa_bridge/`.

---

## القسم الأول: الذكاء الاصطناعي (منفذ)

### كيف يفكر التصميم

- **القسم الرئيسي** (زر «🤖 الذكاء الاصطناعي» في القائمة الرئيسية) فيه
  **أقسام** (أصناف) — وكل قسم هو مجرد **صف في قاعدة البيانات**
  (`ai_sections`). هذا هو سر التوسع: قسم ثالث مستقبلاً = صف جديد من
  لوحة الأدمن، بلا كود.
- كل قسم يحوي:
  - `key` — معرّف فريد (`coding`, `chat`, …)
  - `name_ar / name_en` — الاسم الظاهر للمستخدم.
  - `description_ar / description_en` — **الشرح اليدوي من الأدمن**: ماذا
    يسوي القسم وما مهمته (يظهر للمستخدم داخل القسم).
  - `kind` — `coding` (يرسل الكود **كملف**) أو `chat` (محادثة عادية).
  - `model` — **موديل NanoGPT المحدد لهذا القسم** (تختاره من كتالوج
    nano-gpt.com وتكتبه هنا).
  - `cost_per_message_usd` — **تكلفة الرسالة التقريبية عند المزود**
    (تكتبها يدوياً كما طلبت).
  - `profit_multiplier` — مضاعف الربح، الافتراضي **3** (ربح 3 أضعاف
    التكلفة).
- **سعر الرسالة للمستخدم = التكلفة × (1 + المضاعف)**
  مثال: تكلفة 0.01$ ومضاعف 3 → يدفع المستخدم 0.04$ لكل رسالة،
  وربحك 0.03$.
- **الخصم**: قبل كل رسالة يتحقق البوت من كفاية الرصيد ثم يخصم.
  - لو نجح رد المزود: يُحفظ الرد ويُحتسب الخصم.
  - لو فشل المزود (انقطاع/رصيد NanoGPT/كود خطأ): **يُرجع المبلغ
    تلقائياً** (idempotent — لا يُرجع مرتين) ويظهر للمستخدم خطأ مع زر
    «أعد المحاولة».
- **الجلسات**: لكل مستخدم + قسم جلسة واحدة نشطة، وكل الرسائل تُحفظ
  (`ai_sessions` / `ai_messages`). المستخدم يرجع لأي جلسة من «📜 جلستي»
  ويراها كاملة، ويكمل منها بزر «متابعة آخر جلسة».
- **سياق المحادثة**: يرسل البوت آخر 20 رسالة (قابلة للضبط) كنطاق للمحادثة،
  فالذكاء يتذكر ما قبله.

### إرسال الكود كملف (قسم البرمجة)

تليجرام فيه حد رسائل (4096 حرف) فالكود الطويل يتلخبط. الحل:

1. أوامر النموذج (system prompt) تطلب منه يكتب كل ملف في بلوك كود مستقل
   مع سطر `file: main.py` أول سطر داخل البلوك.
2. الخادم يفكك الرد: يستخرج الملفات المسماة (أو يخمّن الاسم من اللغة:
   python → main.py، html → main.html...).
3. يرسل للمستخدم:
   - ملف واحد → `send_document` مباشرة (main.py).
   - عدة ملفات → كل ملف رسالة + **project.zip** فيها كلها.
   - الشرح النصي (كيف تشغّل) رسالة عادية.

### الإعداد (خطوات الأدمن)

1. **المفتاح**: ضع `NANOGPT_API_KEY` في `.env`
   (من nano-gpt.com ← API). العنوان الافتراضي
   `https://nano-gpt.com/api/v1` — يغيّر من اللوحة لو احتجت.
   المفتاح من اللوحة (لوحة الأدمن ← المتجر ← 🤖 إدارة الذكاء
   الاصطناعي ← 🔌 المزود) يسري على كل الأقسام ويأولوية على .env.
2. **الميزة**: «⚙️ الإعدادات العامة/مركز الإضافات» ← فعّل
   `ai_sections` (الذكاء).
3. **الاقسام**: «🤖 إدارة الذكاء الاصطناعي ← ➕ إضافة قسم»:
   - الأقسام الأساسية المطلوبة:
     - مفاتيح القسمين المزروعين أصلاً في `database/seed.py`:
       `coding` — «برمجة بدون قيود» — نوع: برمجة (يرسل الملفات جاهزة).
       `chat` — «تحدث بدون قيود» — نوع: دردشة. كلاهما **معطّل** حتى تضبط
       مفتاح NanoGPT وتختار الموديل.
     - لا تُنشئ نسخة ثانية باسم `ai_coding`/`ai_chat` (مثال قديم في هذه
       الوثيقة سابقاً) — ستحصل على قسمين مكررين في القائمة.
   - بعد الإنشاء: **🧪 اختبار الاتصال** ثم **تفعيل** القسم.
4. يظهر زر «🤖 الذكاء الاصطناعي» في القائمة الرئيسية تلقائياً عند
   وجود قسم مفعّل واحد على الأقل.

### الأرباح والقياس

- كل خصم حركة في دفتر الأستاذ (`transactions`) بنوع `ai_usage` —
  تظهر في جرد الحسابات.
- «📊 الإحصاءات» في إدارة الذكاء الاصطناعي: لكل قسم عدد الرسائل،
  تكلفة المزود، الإيراد، والربح + إجمالي.
- تغيير الربح مستقبلاً: عدّل `profit_multiplier` في القسم (تعديل)، أو
  تكلفة الرسالة — يسري فورا على الرسائل الجديدة.

### إضافة قسم ثالث (المستقبل)

بدون كود: «➕ إضافة قسم» → معرّف جديد (مثال `images`) → الاسم
والوصف والموديل والتكلفة والمضاعف → تفعيل. يظهر فوراً في قسم
الذكاء الاصطناعي ويخصم من رصيد المستخدم بنفس الآلية.

## القسم الثاني: واتساب — ربط البوتين (منفَّذ)

### المشكلة

البوت الحالي (SD) والبوت الثاني (بوت واتساب) **بوتان مختلفان**. أزرار
تليجرام (callback_data) لا يمكن «نقلها»: الزر الذي أنشأه بوت A لا يستقبل
ضغطه إلا بوت A. الطريقة الوحيدة الصحيحة لعرض **كل أزرار البوت الثاني**
داخل البوت الحالي:

> **جسر (Bridge) HTTP**: البوت الثاني يفتح نقاط API صغيرة تقرأ «قائمة
> أزراره» وتنفّذ «أفعاله» باسم مستخدم تليجرام معين، والبوت الحالي يعيد
> رسمها كأزراره هو ويمرّر الضغطات.

تحتاج «نقطة وصول» واحدة لكل زر يضيفه البوت الثاني مستقبلاً بلا تعديل هنا.

### البنية والملفات

```
┌─────────────────┐  HTTP: Bearer + X-TG-User-Id  ┌────────────────────────────────┐
│  بوت SD (هذا)   │ ────────────────────────────► │ بوت واتساب الثاني              │
│  قسم 📱 واتساب  │ ◄──────────────────────────── │  + wa_bridge/bridge.py         │
│  باقات + أزرار  │   قائمة/أوامر/ملفات/نص       │  + adapter (يقرأ منطقك)        │
└─────────────────┘                                └───────────────┬────────────────┘
                                                                   ▼
                                                       مزوّد الجلسات (BAAS/Baileys…)
```

| الملف | الدور |
|-------|-------|
| `services/wa_bridge_client.py` | عميل الجسر في بوت SD (نقاط العقد + الأخطاء + عدّاد الإخفاقات) |
| `services/whatsapp_section_service.py` | الباقات، الشراء، الربط، التجديد، صحة الجسر، عمليات الأدمن |
| `handlers/whatsapp.py` | واجهة المستخدم: الباقات ← الرقم ← الكود ← قائمة البوت الثاني |
| `handlers/admin/whatsapp.py` | لوحة الأدمن: وصف/سعر/باقات، الجسر، القدرات، المشترون + عملياتهم |
| `wa_bridge/bridge.py` | **الخدمة التي تعمل بجانب البوت الثاني** (FastAPI + تحقق السر) |
| `wa_bridge/adapter.py` | `BridgeAdapter` (والوضع التجريبي `StaticJsonAdapter`) |
| `wa_bridge/adapter_example.py` | مثال كامل قابل للتشغيل — انسخه وعدّل ثلاث دوال |
| `wa_bridge/README_AR.md` | دليل كتابة الـ adapter + الأمان + docker |
| `BRIDGE_SETUP_GUIDE.md` | خطوات ربط البوتين من الصفر للتشغيل |

### عقد الجسر (v2)

كل نقطة تتطلب: `Authorization: Bearer <WA_BRIDGE_SECRET>` و`X-TG-User-Id`.

| النقطة | الطلب | الرد |
|--------|-------|------|
| `GET /ping` | — | `{ok, version, adapter, capabilities}` |
| `POST /link/start` | `{phone}` | `{link_code, instructions}` |
| `GET /link/status` | — | `{state: none\|pending\|linked\|expired, connected_since}` |
| `POST /link/unlink` | — | `{ok}` (اختياري: بوت SD يتحمّل 404) |
| `GET /menu?page=N` | — | `{status_text, menu: [item], page, pages, awaiting_input}` |
| `POST /action` | `{action, payload}` | `{text, files, buttons, menu, page, pages, awaiting_input, alert}` |
| `POST /input` | `{text, payload}` | نفس شكل `/action` |

`item` = `{id, label, data?, kind?, prompt?, url?, disabled?}` و`kind`:
`action` (افتراضي) · `input` (يحتاج نصاً من المستخدم) · `url` (يفتح رابطاً) ·
`back`/`refresh` (يولّدهما بوت SD).

`action` يطابق **معرّف callback_data عند البوت الثاني**، فلا إعادة كتابة لأمر
جديد: زر جديد عندك = سطر في قائمة `menu` عندك.

### القدرات (capabilities) والتوافق الرجعي

الجسر يعلن ما ينفذه، وبوت SD يستخدمه فقط عند الإعلان:

| القدرة | معناها في بوت SD |
|--------|-------------------|
| `input` | زر يطلب كتابة → يلتقط البوت النص ويرسله إلى `/input` |
| `files` | ملفات/صور البوت الثاني تصل كمستندات (رابط أو base64) |
| `links` | أزرار `url` بجانب القائمة |
| `paging` | ترقيم صفحات القائمة (الافتراضي 12 زراً للصفحة) |
| `unlink` | زر «فصل الربط» للمستخدم وللأدمن |

جسر بالإصدار الأول (بلا `/ping` مفصّل) يعمل كما هو: نصوص وأزرار فقط — ولا شيء
ينكسر. «الاختبار» في لوحة الأدمن يعرض القدرات الناقصة.

### تدفق المستخدم داخل بوت SD

1. «📱 واتساب» (`wa:home`) → وصف القسم + حالة الاشتراك. إن لم يكن الجسر مضبوطاً
   تظهر لافتة 🔴 وتُعطَّل أزرار الشراء/الربط — لا يُباع اشتراك في قسم لا يعمل.
2. بلا اشتراك → باقات (`wa:buy:<days>`) → خصم من الرصيد بحركة
   `wa_subscription` في دفتر الأستاذ، والتمدد يركّب فوق المتبقي.
3. «أرسل رقم واتساب» → `POST /link/start` → كود الربط + تعليمات المزود.
   فشل الجسر **يرجع الحالة كما كانت** ويسجّل `link_error` (يظهر للأدمن).
4. «فحص حالة الربط» → `GET /link/status` → عند `linked` يفتح «قائمة بوت الواتساب».
5. كل ضغطة → `POST /action` (أو `/input` للأزرار الكتابية). الرد الذي يحمل
   `menu` يعيد رسم القائمة فوراً، و`awaiting_input` يجعل البوت يسأل المستخدم نصاً.
6. «🔄 تحديث» يعيد الجلب، وضغط زر من قائمة قديمة (بعد إعادة تشغيل أو انتهاء
   الكاش) **يعيد جلب القائمة تلقائياً** بدل أن يبقى الزر ميتاً.

### الدفع والتجديد والمراقبة

- `wa_subscriptions`: صف لكل مستخدم — `phone`، `link_state`، `active_until`،
  `auto_renew`، `last_package_days`، `connected_since`، `link_error`.
- `wa_renewal_cycle` في `bot.py` (كل ساعة): تجديد قبل الانتهاء بـ
  `reminder_hours_before` عند `auto_renew` وكفاية الرصيد (سعر اليوم)، وتنبيه
  واحد عند الانتهاء (`expire_notified_at` يمنع التكرار).
- `wa_bridge_health_cycle` (كل 10 دقائق): يفحص `/ping` وينذر قناة الأدمن عند
  انقطاع الجسر وعند عودته (`bridge_alert_failures` يحدد العتبة).
- لوحة الأدمن: حالة الجسر (🟢/🟠/🔴)، «🧰 القدرات»، والمشترون مع عمليات
  ⏱ تمديد مجاني / 🚫 فصل ربط / 💵 استرداد آخر دفعة (الاسترداد محمي من التكرار
  بمعرّف `wa-refund:<tx>` الفريد).

### لماذا هذا التصميم (وبلماذا غيره)

- ❌ «نسخ أزرار البوت الثاني يدوياً»: كل زر جديد يحتاج تعديلاً هنا.
- ❌ «محاكاة ضغطة على بوت آخر»: مستحيل — ضغطات callback لا تُرسل من بوت لآخر.
- ❌ «تمرير المستخدم عبر بوتين»: واجهتان وحسابان وازدواج في الصرف.
- ✅ **الجسر + adapter**: البوت الثاني مصدر الحقيقة لواجهته، وبوت SD يعرضها
  كما هي. أي زر/أمر يضاف للبوت الثاني يظهر هنا تلقائياً.

### ما لم يُنفَّذ (إن أردته لاحقاً)

- توقيع كل طلب بـ HMAC (timestamp + nonce) بدل سرّ مشترك واحد — يلغي خطر
  سرقة السر. يفضَّل تظبيطه على مستوى الشبكة (loopback/IP allowlist) كما هو الآن.
- مكالمات صوتية/صور مصغّرة (thumb) وردود `media group` من البوت الثاني.
- «push» من البوت الثاني إلى بوت SD (إشعار عند وصول رسالة واتساب) — العقد حالياً
  سحبي (pull) فقط.
